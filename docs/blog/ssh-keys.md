## 1. SSH가 뭐길래

SSH(Secure Shell)는 **다른 컴퓨터의 터미널을 암호화된 통신으로 원격 조작**하는 프로토콜이다.
`ssh root@1.2.3.4` 한 줄이면 서울 데이터센터의 서버 안에서 명령을 치는 것과 같다.
문제는 "접속하려는 네가 진짜 주인이냐"를 증명하는 방법 — 여기서 비밀번호 방식과 키 방식이 갈린다.

- **비밀번호 방식**: 추측 가능하고(무차별 대입), 입력할 때마다 비밀 자체가 검증 대상이 된다.
  공개 서버는 봇들이 하루 종일 비밀번호를 두들긴다 (서버 로그를 열어보면 실감한다).
- **키 방식**: 비밀이 네트워크를 타지 않는다. 아래 원리 참고.

## 2. 원리 — 공개키 암호화 (도장과 견본)

`ssh-keygen`을 실행하면 **수학적으로 짝을 이루는 파일 2개**가 생긴다.

| 파일 | 이름 | 비유 | 취급 |
|---|---|---|---|
| `~/.ssh/id_ed25519` | 개인키(private key) | 도장 | **절대 유출 금지.** 내 컴퓨터 밖으로 나가지 않는다 |
| `~/.ssh/id_ed25519.pub` | 공개키(public key) | 도장 견본 | 어디에 공개해도 안전. 서버·GitHub에 올리는 건 이것 |

접속 흐름 (challenge–response):

```
1. 나:    "접속하고 싶어" (id_ed25519.pub 견본이 서버에 미리 등록돼 있음)
2. 서버:  임의의 문제(챌린지)를 만들어 던진다
3. 나:    개인키로 그 문제에 서명해서 답을 보낸다   ← 개인키 자체는 안 보냄!
4. 서버:  등록된 공개키로 "이 서명이 짝이 맞는 개인키에서 나왔는지" 검증
```

핵심: **비밀(개인키)이 한 번도 전송되지 않는다.** 도청해도 얻을 게 없고,
챌린지가 매번 달라서 답을 녹음해 재사용(replay)할 수도 없다.
공개키에서 개인키를 역산하는 건 현재 계산 능력으로 불가능하다.

같은 원리가 쓰이는 곳: GitHub SSH 인증, TLS 인증서(HTTPS), JWT 서명, 결제 웹훅 서명 검증.
한 번 이해하면 백엔드 보안 전반이 같은 그림으로 보인다.

## 3. 만드는 법과 옵션

```sh
ssh-keygen -t ed25519 -C "taerim-macbook"
```

| 옵션 | 의미 | 비고 |
|---|---|---|
| `-t ed25519` | 키 알고리즘 | 아래 §4 — 요즘은 이거 하나면 된다 |
| `-C "..."` | 주석(라벨) | 공개키 끝에 붙는 식별용 텍스트. "어느 기계의 키인지" 적는 관례 (이메일도 흔함) |
| `-f 경로` | 저장 위치 | 생략 시 `~/.ssh/id_<알고리즘>` |
| `-N "암호"` | passphrase | 개인키 파일 자체에 거는 잠금. `-N ""` = 없음 (§5) |
| `-b 4096` | 키 길이(bit) | **RSA에서만 의미** 있음. ed25519는 길이 고정이라 불필요 |

실행하면 나오는 질문들은 전부 엔터로 기본값 수락해도 된다.
생성 후 확인:

```sh
ls -l ~/.ssh/           # id_ed25519 (600 권한), id_ed25519.pub
cat ~/.ssh/id_ed25519.pub   # 서버/GitHub에 붙여넣을 한 줄
```

개인키 권한은 반드시 본인만 읽기(`600`)여야 한다 — ssh가 권한이 느슨하면 접속을 거부한다.

### 서버에 공개키를 등록하는 3가지 방법

1. **호스팅 콘솔에서** (Vultr/AWS 등): 서버 생성 시 공개키 붙여넣기 → 자동으로 심어짐. 제일 편함
2. **ssh-copy-id**: 이미 비밀번호 접속이 되는 서버라면 `ssh-copy-id root@<IP>` 한 줄
3. **수동**: 서버의 `~/.ssh/authorized_keys` 파일에 공개키 한 줄 추가 — 결국 1·2도 이 파일에 쓰는 것

`authorized_keys` = "이 견본들과 짝이 맞는 도장은 들여보내라"는 출입 허가 명단이다.

### 처음 접속할 때 뜨는 질문의 정체

```
The authenticity of host '1.2.3.4' can't be established. ... Are you sure? (yes/no)
```

이건 반대 방향 검증이다 — **서버가 진짜 그 서버인지**를 내가 확인하는 것.
yes 하면 서버의 공개키가 내 `~/.ssh/known_hosts`에 저장되고, 이후 서버가 바꿔치기당하면
(중간자 공격) 경고가 뜬다. 요약: `authorized_keys`는 서버가 나를, `known_hosts`는 내가 서버를 믿는 명단.

## 4. 키 종류 비교 — 왜 ed25519인가

| 알고리즘 | 상태 | 특징 |
|---|---|---|
| **Ed25519** | **현재 표준, 기본 선택** | 짧고(공개키 한 줄 68자) 빠르고 안전. 2014년 OpenSSH 6.5부터. 키 길이 고민 자체가 없음 |
| RSA | 구형이지만 현역 | 1977년생. **3072bit 이상**이면 아직 안전. 아주 오래된 장비와의 호환용. 키가 길고 느림 |
| ECDSA | 애매한 중간 세대 | 타원곡선 기반. NIST 곡선에 대한 신뢰 논쟁 + 구현 실수에 취약한 설계라 ed25519에 밀림 |
| DSA (ssh-dss) | **사용 금지** | 낡고 약함. OpenSSH가 기본 비활성화 |
| ed25519-sk / ecdsa-sk | 특수 | YubiKey 같은 **하드웨어 보안키**에 개인키를 넣는 변형 — 개인키가 컴퓨터에도 없음 |

결론: 새로 만들면 **ed25519**. RSA를 고를 이유는 "상대 시스템이 낡아서 ed25519를 못 받을 때"뿐이고,
그마저 요즘은 드물다. (GitHub, Vultr, AWS 전부 ed25519 지원.)

## 5. passphrase와 ssh-agent — 도장에 자물쇠 걸기

passphrase는 **개인키 파일 자체를 암호화**하는 비밀번호다. 노트북을 통째로 도난당해도
passphrase를 모르면 개인키를 못 쓴다. 대신 키를 쓸 때마다 입력해야 하는 불편이 생기는데,
그걸 해결하는 게 **ssh-agent** — 한 번 풀어두면 세션 동안 기억해준다. 맥은 Keychain 연동으로
사실상 자동이다:

```sh
ssh-keygen -t ed25519 -C "..."          # passphrase 입력 (이번엔 설정)
ssh-add --apple-use-keychain ~/.ssh/id_ed25519   # 맥 키체인에 저장 — 이후 입력 불필요
```

선택 기준: 데모/실험용 키는 passphrase 없이도 괜찮지만, **GitHub·프로덕션 서버에 쓰는
키라면 거는 것을 권장**한다.

## 6. 운영 팁

- **유출됐다고 의심되면**: 개인키를 지우는 게 아니라, **서버들의 authorized_keys에서
  해당 공개키를 제거**하는 게 조치다 (출입 명단에서 빼기). 그리고 새 키 발급.
- **키 재사용 vs 분리**: 개인 개발자는 기계당 키 1개(맥북 키 하나로 GitHub+서버들)가 관리하기
  현실적이다. 회사/프로덕션은 용도별 분리 + 주기적 교체가 정석.
- 백업 주의: 개인키를 클라우드 드라이브/메신저로 옮기는 순간 "유출 금지" 전제가 깨진다.
  기계가 바뀌면 복사가 아니라 **새 키를 만들어 등록**하는 게 맞다.
